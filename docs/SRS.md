## 1. Introduction

### 1.1 Purpose

This document specifies the software requirements for **PeopleCore**, a web-based Human Resources Management System (HRMS). It serves as the authoritative reference for system design, Figma prototyping, frontend implementation, and backend development.

### 1.2 Intended Audience

- Workshop facilitators and assessors
- Frontend and backend developers working on the implementation
- UI/UX designers producing the Figma prototype

### 1.3 Definitions and Abbreviations

| Term | Definition |
|---|---|
| HR Admin | A privileged system user with full access to all modules |
| Line Manager | A mid-tier role that performs first-stage leave approval for direct reports |
| Employee | A standard system user with access to their own data only |
| Leave Request | A formal request by an Employee for time off |
| LeaveType | A configurable leave category managed by HR Admin |
| Payslip | A monthly pay record generated by HR Admin |
| PayrollProfile | Banking and salary details for an Employee |
| LeaveEntitlement | Company-wide annual allowance for a given leave type |
| EmployeeLeaveEntitlement | Per-employee override of the company-wide entitlement |
| PublicHoliday | A company-wide configured public holiday for a specific calendar date |
| AuditLog | A timestamped record of a significant system action |
| Firebase Auth | Google Firebase Authentication service |
| Firestore | Google Cloud Firestore NoSQL database |
| Custom Claims | Role metadata stored in a Firebase Auth token |
| ADR | Architectural Decision Record |

## 2. Project Overview and Objectives

### 2.1 Overview

PeopleCore is a web-based HRMS designed for companies with 100–200 employees. It centralises three core HR functions — employee record management, leave management, and payroll administration — into a single, role-controlled application.

### 2.2 Objectives

1. Provide HR Admin with a unified interface to manage employee records, approve leave requests, and generate payslips.
2. Provide Line Managers with first-stage leave approval capability for their direct reports.
3. Provide Employees with self-service access to their own profile, leave history, and payslips.
4. Enforce role-based access control so that employees cannot access other employees' data.
5. Deliver a functional, demonstrable system within the workshop deadline (August 10, 2026).

### 2.3 Technology Stack

| Layer | Technology |
|---|---|
| Frontend | React 18 + Vite |
| Backend | Node.js + Express |
| Database | Google Cloud Firestore |
| Authentication | Firebase Authentication |
| Language | TypeScript (recommended) / JavaScript |

## 4. User Roles and Responsibilities

### 4.1 HR Admin

The HR Admin has full administrative access across all modules.

**Responsibilities:**
- Create, edit, and deactivate Employee and Line Manager accounts (sets initial password directly)
- Manage company-wide and per-employee leave entitlements
- Create, edit, and delete leave types
- Create, edit, and delete public holidays
- View all leave requests; perform final approval or rejection (stage 2)
- Create and manage PayrollProfiles
- Generate, itemise, and publish payslips
- View the full audit log
- View the HR Admin dashboard

**Access:** All modules, all employee data.

### 4.2 Line Manager

A Line Manager is an Employee assigned the `manager` role. They have elevated access over their direct reports' leave requests only.

**Responsibilities:**
- View leave requests submitted by their direct reports
- Perform first-stage approval or rejection of those requests
- View the Line Manager dashboard

**Access:** Own employee data (same as Employee) plus leave request management for direct reports. Cannot access payroll data, create/delete employee records, or manage leave types, entitlements, or public holidays.

### 4.3 Employee

An Employee has read access to their own data and limited write access.

**Responsibilities:**
- View their own employee profile
- Edit their own phone number
- Request a password reset email
- Submit leave requests (full-day and half-day)
- Cancel their own pending leave requests
- View their own leave history and remaining balance
- View their own published payslips
- View the Employee dashboard

**Access:** Own record only. Cannot view or modify any other employee's data.

## 5. Functional Requirements

### 5.1 Authentication

| ID | Requirement |
|---|---|
| AUTH-01 | The system shall authenticate users via Firebase Authentication using email and password. |
| AUTH-02 | HR Admin shall create user accounts by providing an email address and setting an initial password directly. |
| AUTH-03 | Each user account shall be assigned a role (`admin`, `manager`, or `employee`) stored as a Firebase custom claim at account creation. |
| AUTH-04 | The backend shall verify the Firebase ID token on every API request and reject requests with an invalid or missing token with HTTP 401. |
| AUTH-05 | The backend shall enforce role-based access on every protected endpoint, returning HTTP 403 for unauthorised role access. |
| AUTH-06 | Role claims are set at account creation and are not self-assignable by users. |
| AUTH-07 | An Employee or Line Manager shall be able to request a password reset email via the login screen. The system shall trigger Firebase Authentication's built-in `sendPasswordResetEmail` flow, sending a reset link to the user's registered email address. |

### 5.2 Dashboard

| ID | Requirement |
|---|---|
| DASH-01 | Upon login, HR Admin shall see a dashboard showing: total active employee headcount, count of leave requests with status `manager_approved` awaiting final approval, and count of draft (unpublished) payslips. |
| DASH-02 | Upon login, a Line Manager shall see a dashboard showing: count of pending leave requests from their direct reports awaiting first-stage review. |
| DASH-03 | Upon login, an Employee shall see a dashboard showing: their leave balance for all capped leave types for the current year, a list of their pending leave requests, and the status of their most recent payslip. |
| DASH-04 | Dashboard data shall be read-only aggregations over existing data. No new entities are required. |

### 5.3 Employee Management

| ID | Requirement |
|---|---|
| EMP-01 | HR Admin shall be able to create a new Employee record with fields: `fullName`, `email`, `phone`, `department`, `jobTitle`, `employmentType`, `startDate`, `status`, `nationalId`, `address`, `emergencyContact`, and optionally `lineManagerId`. |
| EMP-02 | HR Admin shall be able to edit any field on any Employee record. |
| EMP-03 | HR Admin shall be able to deactivate an Employee by setting `status` to `inactive`. |
| EMP-04 | HR Admin shall be able to delete an Employee record. |
| EMP-05 | HR Admin shall be able to view a list of all employees, filterable by `status` and `department`. |
| EMP-06 | An Employee shall be able to view their own profile. |
| EMP-07 | An Employee shall be able to edit only their own `phone` field. All other fields are read-only for the Employee. |
| EMP-08 | An Employee shall not be able to view any other employee's profile. |
| EMP-09 | The `employmentType` field shall accept one of: `full-time`, `part-time`, `contract`. |
| EMP-10 | The `status` field shall accept one of: `active`, `inactive`. |
| EMP-11 | The `department` field is a free-text string. The recommended standard values (Engineering, HR, Finance, Operations, Sales) are guidance only and are not enforced by the system. |
| EMP-12 | The `emergencyContact` field shall store an object with: `name` (string), `phone` (string), and `relationship` (string). |
| EMP-13 | HR Admin shall be able to assign a Line Manager to an Employee by setting the `lineManagerId` field to the `employeeId` of a user with the `manager` role. |


### 5.4 Leave Management

| ID | Requirement |
|---|---|
| LEAVE-01 | HR Admin shall be able to create, edit, and delete leave types. Each leave type has a `name`, an `isCapped` flag, and a `defaultDaysPerYear` (used only when `isCapped` is `true`). |
| LEAVE-02 | The system shall seed three default leave types at setup: `Annual` (capped), `Medical` (capped), and `Unpaid` (uncapped). |
| LEAVE-03 | Leave types with `isCapped: false` shall have no entitlement cap and no tracked balance. |
| LEAVE-04 | HR Admin shall be able to configure a company-wide annual entitlement (in days) for any capped leave type via the LeaveEntitlement collection. |
| LEAVE-05 | HR Admin shall be able to set a per-employee entitlement override (EmployeeLeaveEntitlement) for any capped leave type, overriding the company-wide default for that specific employee. |
| LEAVE-06 | An Employee shall be able to submit a leave request specifying: `leaveTypeId`, `startDate`, `endDate`, and `reason`. |
| LEAVE-07 | An Employee shall be able to submit a half-day leave request by setting `isHalfDay: true` and specifying `halfDayPeriod` (`morning` or `afternoon`). Half-day requests must have `startDate = endDate`. |
| LEAVE-08 | The system shall calculate `numberOfDays` at submission time: `0.5` for half-day requests; for full-day requests, the count of weekdays (Monday–Friday) between `startDate` and `endDate` inclusive, excluding any configured PublicHoliday dates that fall on weekdays within that range. |
| LEAVE-09 | A newly submitted leave request shall have status `pending`. |
| LEAVE-10 | If the submitting Employee has an assigned Line Manager (`lineManagerId` is set), the request shall require Line Manager first-stage action before HR Admin final action. If no Line Manager is assigned, the request goes directly to HR Admin. |
| LEAVE-11 | A Line Manager shall be able to approve a `pending` leave request from a direct report, setting status to `manager_approved` and recording `managerId` and `managerActionAt`. |
| LEAVE-12 | A Line Manager shall be able to reject a `pending` leave request from a direct report, setting status to `rejected` and recording `managerId`, `managerActionAt`, and `managerRejectionReason`. |
| LEAVE-13 | HR Admin shall be able to approve a `manager_approved` leave request (or a `pending` request where no Line Manager is assigned), setting status to `approved` and recording `reviewedBy` and `reviewedAt`. |
| LEAVE-14 | HR Admin shall be able to reject a `manager_approved` or `pending` leave request, setting status to `rejected` and recording `reviewedBy`, `reviewedAt`, and `rejectionReason`. |
| LEAVE-15 | HR Admin shall be able to modify or delete any leave request regardless of its current status. |
| LEAVE-16 | An Employee may only transition a leave request from `pending` to `cancelled`. An Employee shall not perform any other status transition or modification on any leave request. |
| LEAVE-17 | The system shall compute an Employee's leave balance on demand for a given capped leave type as: the effective entitlement (per-employee override if set, otherwise company-wide default) minus the sum of `numberOfDays` for all approved requests in the current calendar year for that leave type. This value is not stored. |
| LEAVE-18 | HR Admin shall be able to view all leave requests across all employees, filterable by status and leave type. |
| LEAVE-19 | A Line Manager shall be able to view leave requests submitted by their direct reports. |
| LEAVE-20 | An Employee shall be able to view only their own leave requests. |
| LEAVE-21 | HR Admin shall be able to create, edit, and delete PublicHoliday records, specifying a `name`, `date`, and `year` for each. |
| LEAVE-22 | HR Admin shall be able to view all configured public holidays, filterable by `year`. |

### 5.5 Payroll

| ID | Requirement |
|---|---|
| PAY-01 | HR Admin shall be able to create a PayrollProfile for an Employee, recording: `bankAccountNumber`, `bankName`, and `baseSalary`. |
| PAY-02 | HR Admin shall be able to edit a PayrollProfile. |
| PAY-03 | HR Admin shall be able to generate a Payslip for an Employee for a given month and year, populated with the current `baseSalary` as a snapshot. |
| PAY-04 | HR Admin shall be able to add, edit, and remove deduction line items on a draft Payslip. Each deduction has a `label` (string) and `amount` (number). |
| PAY-05 | The system shall compute `netSalary` as `baseSalary − sum(deductions[].amount)`. This value is stored on the Payslip record. |
| PAY-06 | Deductions are entered manually by HR Admin. The system performs no automatic tax, EPF, or SOCSO calculations. |
| PAY-07 | A newly created Payslip shall have status `draft`. |
| PAY-08 | HR Admin shall be able to publish a Payslip by setting its status to `published`. Once published, the Payslip is visible to the Employee. |
| PAY-09 | An Employee shall be able to view only their own published payslips. Draft payslips are not visible to Employees. |
| PAY-10 | HR Admin shall be able to view all payslips for all employees. |
| PAY-11 | PayrollProfile data (bank account details, base salary) shall not be visible to the Employee in the UI. |

### 5.6 Audit Log

| ID | Requirement |
|---|---|
| AUDIT-01 | The system shall write an AuditLog entry for every create, update, delete, and status-transition operation across all modules. |
| AUDIT-02 | Each AuditLog entry shall record: `actorId`, `actorRole`, `action`, `targetType`, `targetId`, `timestamp`, and `diff` (changed fields with before/after values, omitted for create/delete). |
| AUDIT-03 | HR Admin shall be able to view the full audit log, filterable by `targetType`, `actorId`, and date range. |
| AUDIT-04 | Line Managers and Employees shall not have access to the audit log. |
| AUDIT-05 | AuditLog entries shall be immutable — they may not be edited or deleted by any user role. |

## 6. Non-Functional Requirements

### 6.1 Performance

| ID | Requirement |
|---|---|
| PERF-01 | API responses for read operations (employee list, leave requests, payslips) shall complete within 2 seconds under normal load for a dataset of up to 200 employees. |
| PERF-02 | The React frontend shall achieve an initial load time of under 3 seconds on a standard broadband connection. |
| PERF-03 | Dashboard aggregation queries shall complete within 3 seconds. |

### 6.2 Security

| ID | Requirement |
|---|---|
| SEC-01 | All API endpoints (except the login and password reset request flows) shall require a valid Firebase ID token. |
| SEC-02 | Role-based access control shall be enforced server-side on every endpoint. Client-side UI restrictions alone are not sufficient. |
| SEC-03 | An Employee shall not be able to read or write any other employee's data through any API endpoint, regardless of UI state. |
| SEC-04 | PayrollProfile and Payslip data shall be accessible via API only to HR Admin, except that an Employee may retrieve their own published payslips. |
| SEC-05 | Passwords are managed by Firebase Authentication. The backend shall not store, log, or transmit plaintext passwords. |
| SEC-06 | Firebase custom claims (`role`) shall be set only by the backend (HR Admin-triggered account creation). No client-side claim mutation is permitted. |
| SEC-07 | HTTPS shall be used for all client-server communication in production. |
| SEC-08 | A Line Manager shall only be able to act on leave requests where the submitting employee's `lineManagerId` matches the Line Manager's own `employeeId`. |

### 6.3 Scalability

| ID | Requirement |
|---|---|
| SCALE-01 | The system shall support a company size of 100–200 employees without architectural changes. |
| SCALE-02 | Firestore collections shall be structured to allow efficient per-employee and per-status queries without full collection scans. |
| SCALE-03 | The Express backend shall be stateless so that horizontal scaling (multiple instances) is possible without session-sharing concerns. |

### 6.4 Usability

| ID | Requirement |
|---|---|
| USE-01 | The application shall be usable on modern desktop browsers (Chrome, Firefox, Edge — latest two versions). Mobile responsiveness is not required for this build. |
| USE-02 | Forms shall display inline validation errors before submission. |
| USE-03 | Destructive actions (delete employee, delete leave request) shall require a confirmation step. |

### 6.5 Reliability

| ID | Requirement |
|---|---|
| REL-01 | The system shall display a user-friendly error message when an API call fails, rather than a raw error or blank screen. |
| REL-02 | Authentication state shall persist across browser refreshes using Firebase's built-in session persistence. |

## 7. Use Cases and Workflows

### UC-01: HR Admin Creates a User Account

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in.

1. HR Admin navigates to Employee Management and selects "Add Employee" (or "Add Line Manager").
2. HR Admin fills in `fullName`, `email`, `phone`, `department`, `jobTitle`, `employmentType`, `startDate`, `nationalId`, `address`, `emergencyContact`, optionally `lineManagerId`, and sets an initial password.
3. System creates a Firebase Auth user with the appropriate role custom claim (`employee` or `manager`).
4. System creates an Employee document in Firestore.
5. HR Admin is returned to the employee list, which now includes the new user.

**Postcondition:** User can log in with the provided credentials.

---

### UC-02: Employee Views Their Profile

**Actor:** Employee  
**Precondition:** Employee is logged in.

1. Employee navigates to "My Profile".
2. System fetches their Employee record via `GET /employees/:employeeId` (token-verified, own record only).
3. Employee sees their details including `nationalId`, `address`, and `emergencyContact`. `phone` has an edit button; all other fields are display-only.

---

### UC-03: Employee Updates Their Phone Number

**Actor:** Employee  
**Precondition:** Employee is logged in and viewing their profile.

1. Employee clicks edit on the `phone` field, enters a new value, and submits.
2. System sends `PATCH /employees/:employeeId/phone` with the new value.
3. Backend verifies the token, confirms the `employeeId` in the path matches the requesting user's own ID, and updates only the `phone` field.
4. Profile view refreshes with the updated phone number.

**Error case:** If the Employee attempts to update any field other than `phone`, the backend returns HTTP 403.

---

### UC-04: User Requests a Password Reset

**Actor:** Employee or Line Manager  
**Precondition:** User is on the login screen and knows their registered email address.

1. User clicks "Forgot password?" on the login screen.
2. User enters their registered email address and submits.
3. System calls Firebase Authentication's `sendPasswordResetEmail` with the provided address.
4. User receives a password reset link by email and follows it to set a new password.

**Note:** The backend does not handle the reset link itself — Firebase Auth manages the token and the reset flow end-to-end.

---

### UC-05: Employee Submits a Leave Request

**Actor:** Employee  
**Precondition:** Employee is logged in.

1. Employee navigates to "Leave" and selects "New Request".
2. Employee selects `leaveTypeId`, `startDate`, `endDate`, optionally toggles "Half day" and selects `halfDayPeriod`, and enters a `reason`.
3. System calculates `numberOfDays` (0.5 for half-day; weekday count excluding configured public holidays for full-day).
4. System displays the computed `numberOfDays` and the employee's remaining balance for the selected leave type (if capped).
5. Employee confirms and submits.
6. System creates a LeaveRequest document with status `pending` and `submittedAt` timestamp.
7. Leave list refreshes showing the new pending request.

**Error case:** If `startDate` is after `endDate`, or if `isHalfDay` is true but `startDate ≠ endDate`, the form shows a validation error and does not submit.

---

### UC-06: Line Manager Reviews a Leave Request

**Actor:** Line Manager  
**Precondition:** Line Manager is logged in; at least one direct report has a `pending` leave request.

1. Line Manager navigates to "Leave Approvals" and views the list of pending requests from their direct reports.
2. Line Manager opens a request and reviews the details.
3. Line Manager selects "Approve" or "Reject".
   - On Approve: status → `manager_approved`, `managerId` and `managerActionAt` are recorded.
   - On Reject: Line Manager enters a `managerRejectionReason`; status → `rejected`, all manager action fields are recorded.
4. Leave list refreshes.

**Error case:** If the Line Manager attempts to act on a request from an employee who is not their direct report, the API returns HTTP 403.

---

### UC-07: HR Admin Performs Final Approval or Rejection

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in; at least one leave request has status `manager_approved` (or `pending` for employees without a Line Manager).

1. HR Admin navigates to "Leave Management" and views the list of requests awaiting final review.
2. HR Admin opens a request and reviews the details.
3. HR Admin selects "Approve" or "Reject".
   - On Approve: status → `approved`, `reviewedBy` and `reviewedAt` are recorded.
   - On Reject: HR Admin enters a `rejectionReason`; status → `rejected`, all review fields are recorded.
4. Leave list refreshes.

---

### UC-08: Employee Cancels a Pending Leave Request

**Actor:** Employee  
**Precondition:** Employee has a leave request with status `pending`.

1. Employee navigates to their leave history.
2. Employee selects a pending request and chooses "Cancel".
3. System confirms the action with a prompt.
4. System sets status → `cancelled`.
5. Leave list refreshes. The request is shown as cancelled.

**Error case:** If the request status is not `pending`, the cancel option is not shown and the API returns HTTP 400 if attempted directly.

---

### UC-09: HR Admin Generates and Publishes a Payslip

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in; employee has a PayrollProfile with `baseSalary` set.

1. HR Admin navigates to "Payroll" and selects an employee.
2. HR Admin selects "Generate Payslip" and chooses month and year.
3. System creates a Payslip document with status `draft`, copying the current `baseSalary` as a snapshot.
4. HR Admin adds deduction line items (e.g. `{ label: "Income Tax", amount: 300 }`).
5. System displays computed `netSalary` = `baseSalary − sum(deductions)`.
6. HR Admin reviews and selects "Publish".
7. System sets Payslip status → `published`.
8. Payslip is now visible to the Employee in their payslip list.

---

### UC-10: Employee Views a Payslip

**Actor:** Employee  
**Precondition:** At least one published payslip exists for the employee.

1. Employee navigates to "My Payslips".
2. System fetches payslips via `GET /payslips?employeeId=:id&status=published`.
3. Employee sees a list of published payslips ordered by year/month descending.
4. Employee opens a payslip and sees: month/year, `baseSalary`, itemised deductions, and `netSalary`.

**Note:** Draft payslips are not returned by this endpoint for Employee role requests.

---

### UC-11: HR Admin Views the Dashboard

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in.

1. HR Admin lands on the dashboard after login.
2. System queries:
   - Total active employee count (`status = 'active'`)
   - Count of leave requests with `status = 'manager_approved'`
   - Count of payslips with `status = 'draft'`
3. Dashboard displays the three counts as summary cards.

---

### UC-12: Employee Views the Dashboard

**Actor:** Employee  
**Precondition:** Employee is logged in.

1. Employee lands on the dashboard after login.
2. System queries:
   - Leave balances for all capped leave types for the current calendar year
   - Own leave requests with `status = 'pending'`
   - Most recent payslip (by year/month) and its status
3. Dashboard displays leave balance summary, pending request list, and latest payslip status.

---

### UC-13: HR Admin Views the Audit Log

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in.

1. HR Admin navigates to "Audit Log".
2. HR Admin optionally filters by `targetType`, `actorId`, or date range.
3. System returns matching AuditLog entries ordered by `timestamp` descending.
4. HR Admin reviews the log to trace who made which changes and when.

---

### UC-14: HR Admin Manages Leave Types

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in.

1. HR Admin navigates to "Leave Settings" and views existing leave types.
2. To create: HR Admin enters `name`, sets `isCapped`, and if capped enters `defaultDaysPerYear`. System creates a LeaveType document.
3. To edit: HR Admin updates any field on an existing leave type.
4. To delete: HR Admin confirms deletion. The leave type is removed (existing leave requests referencing it retain their `leaveTypeId` for historical accuracy).

---

### UC-15: HR Admin Sets a Per-Employee Leave Entitlement Override

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in; the target leave type is capped.

1. HR Admin navigates to an employee's profile and selects "Leave Entitlements".
2. HR Admin selects a capped leave type and enters an override value for `daysPerYear`.
3. System creates or updates an EmployeeLeaveEntitlement document for that employee and leave type.
4. The employee's leave balance for that type is now computed using the override value instead of the company-wide default.

---

### UC-16: HR Admin Manages Public Holidays

**Actor:** HR Admin  
**Precondition:** HR Admin is logged in.

1. HR Admin navigates to "Leave Settings" and selects "Public Holidays".
2. HR Admin views the list of configured public holidays, optionally filtered by year.
3. To create: HR Admin enters the holiday `name` and `date`. System creates a PublicHoliday document with the `year` derived from the date.
4. To edit: HR Admin updates the `name` or `date` of an existing holiday.
5. To delete: HR Admin confirms deletion. Future leave submissions will no longer exclude that date. Existing `numberOfDays` values on submitted requests are not retroactively recalculated.

## 9. System Architecture

### 9.1 Overview

```
┌─────────────────────┐       HTTPS        ┌──────────────────────┐
│   React + Vite      │ ──────────────────▶ │  Express (Node.js)   │
│   (Frontend)        │                     │  (REST API)          │
│                     │ ◀────────────────── │                      │
└─────────────────────┘       JSON          └──────────┬───────────┘
                                                        │ Firebase Admin SDK
                                             ┌──────────▼───────────┐
                                             │  Google Firestore    │
                                             │  Firebase Auth       │
                                             └──────────────────────┘
```

### 9.2 Request Flow

1. React app authenticates via Firebase Auth SDK (email/password).
2. Firebase returns an ID token to the client.
3. React includes the ID token in the `Authorization: Bearer <token>` header on every API request.
4. Express middleware verifies the token using the Firebase Admin SDK.
5. Middleware attaches the decoded role claim to the request context.
6. Route handler enforces role-based access and executes the Firestore operation.
7. After a successful write operation, the route handler writes an AuditLog entry.
8. Response is returned as JSON to the React frontend.

### 9.3 Architectural Decision

See `docs/adr/0001-express-api-over-direct-firestore.md` for the rationale behind routing all Firestore access through the Express API rather than using the Firestore client SDK directly from React.

## 10. Constraints and Assumptions

| # | Constraint / Assumption |
|---|---|
| C-01 | The system targets companies with 100–200 employees. Performance requirements are scoped to this range. |
| C-02 | Only desktop browsers are supported (Chrome, Firefox, Edge — latest two versions). |
| C-03 | A single HR Admin account is assumed for this build. Multi-admin support is not explicitly designed for but is not excluded. |
| C-04 | Company-wide leave entitlements are the default; per-employee overrides take precedence when set. |
| C-05 | Role changes (admin ↔ manager ↔ employee) require the affected user's Firebase ID token to refresh before the new role takes effect. This delay is accepted. |
| C-06 | The system does not perform any payroll tax, EPF, or SOCSO calculations. All deductions are manually entered by HR Admin. |
| C-07 | `numberOfDays` on a leave request excludes weekends and any configured public holidays that fall on weekdays within the requested range. |
| C-08 | Half-day leave requests must have `startDate = endDate`. |
| C-09 | If an employee has no assigned Line Manager, their leave requests bypass the `manager_approved` stage and go directly to HR Admin. |
| C-10 | AuditLog entries are immutable. No user role may edit or delete them. |
| C-11 | The system is a workshop project. Production-grade concerns such as rate limiting and disaster recovery are out of scope. |
